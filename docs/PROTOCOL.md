# Implemented wire protocols

This document describes only what the server implements. It does not contain
recovered client strings, keys or game content. The evidence is the pinned
GameSpy SDK client source and the static analysis recorded in the research
workspace.

## Availability (UDP 27900)

The client sends `09`, two reserved bytes and a NUL-terminated game name. The
server replies `FE FD 09` followed by a big-endian 32-bit disabled-service
bitmap. M1 always replies zero (all services available). A malformed probe is
ignored and logged.

## AuthService certificate login (TCP 443, SSL 3.0 / RC4-MD5)

One HTTP/1.x POST per TLS connection, with `Content-Length` and a `SOAPAction`
containing the certificate-login method name. The parser accepts prefixed SOAP element names and
reads `version`, `gameid`, `partnercode`, `namespaceid` and the ticket wrapper
`Value`. The account ticket is not validated and is never logged.

The reply is a minimal SOAP envelope with the method result element, `responseCode=0`,
`authToken` and `partnerChallenge`. Both values are freshly generated 64-character
hex strings. The token/challenge pair is kept in memory for GPCM.

## GPCM (TCP 29900)

The client connects and waits for the server:

```text
\lc\1\challenge\<server challenge>\id\1\final\
```

`\id\1` is required: the SDK only dispatches a message to the connect operation
when an `\id\` key is present, and the connect operation is always ID 1. The
server challenge is ten decimal digits.

The client answers with the pre-authenticated login:

```text
\login\\challenge\<user challenge>\authtoken\<AuthService token>\
partnerid\<n>\response\<md5>\port\<n>\productid\<n>\gamename\<name>\
namespaceid\<n>\sdkrevision\<n>\quiet\<n>\id\1\final\
```

The server looks up the token, computes:

```text
passwordHash = MD5(partnerChallenge)
proof = MD5(passwordHash + 48 spaces + authToken + serverChallenge +
            userChallenge + passwordHash)
```

and replies:

```text
\lc\2\sesskey\<n>\userid\<n>\profileid\<n>\uniquenick\<name>\
proof\<32 lowercase hex>\id\1\final\
```

The SDK verifies `proof` and treats a mismatch as a fatal server-authentication
failure, so the proof is not optional. `uniquenick` is generated locally as
`player<profileid>`. The server ignores the client's `response` field because
the token is minted by this service and is unguessable; this is an intentional
M1 simplification, documented as a known difference.

After login the connection stays open. The server answers `\ka\\final\` to a
client keep-alive, closes on `\logout\`, and ignores other unsolicited commands
(Peer/room operations are not implemented). AuthService tokens expire after
15 minutes in memory; a restart invalidates them.

## GPCM error response

For an unknown or expired token the server sends:

```text
\error\\err\266\errmsg\unknown auth token\final\
```

`266` is the SDK's `GP_LOGIN_BAD_PREAUTH` value.

## PeerChat (TCP 6667)

The Peer SDK uses a line protocol modelled on IRC. Lines end in CRLF, and only
printable ASCII is accepted. The only implemented flow is the pre-authenticated
Peer login; channel and room operations are logged and ignored.

The connection starts in plaintext. The client sends:

```text
CRYPT des 1 <gamename>
```

The server answers with the last plaintext line:

```text
:s 705 * <client-out-key> <client-in-key>
```

Both keys are 24 printable characters generated by the server. From this point
each direction is encrypted with the GameSpy stream cipher from `chatCrypt.c`.
The key is the key string XORed with the title secret, cycling the secret. The
client measures the key string's length before the XOR and passes that length
to `gs_prepare_key`, so a zero byte produced by the XOR stays in the key rather
than truncating it. The generated keys are chosen so the XOR is never zero,
which is defensive for builds that might measure the key after the XOR. The
cipher state persists across writes, so one state is kept per direction. The
client's outbound direction uses `<client-out-key>`; the server's outbound
direction uses `<client-in-key>`.

The client then sends `LOGINPREAUTH <authToken> <partnerChallenge>`. The server
resolves the AuthService token in memory and requires the partner challenge to
match the value minted with that token. On success it sends:

```text
:s 707 <nick> <userid> <profileid>
```

`<nick>` is generated locally as `player<profileid>`. The client then sends
`USRIP`, which is answered with:

```text
:s 302 <nick> :<user>@<ip>
```

The SDK consumes only the address after `@`. The client then sends
`USER <user> <mode> <server> :<real name>` and `NICK <nick>`; once both have
been seen the server sends:

```text
:s 001 <nick> :<text>
```

which completes the chat connect operation. A `CDKEY <key>` line is answered
with `:s 706 <nick> 0 :Accepted`; the key is not validated. `PING` receives PONG,
`QUIT` closes the connection, and unknown commands are logged and receive numeric 421.

A rejected login receives:

```text
:s 708 * :<reason>
```

The message contains no token or challenge value. The title secret is supplied
as `peerchat.title_secret` in the local configuration (1 to 31 printable ASCII
bytes) and must match the value compiled into the client. It is not distributed
with this server and is not needed for the loopback tests, which use a synthetic
value. A wrong secret produces a valid-looking `:s 705` line but undecryptable
traffic in both directions.

## 2026-10-28 console corrections

The target uses ordinary secure PeerChat registration (CRYPT, USRIP, USER/NICK), not LOGINPREAUTH. The latter remains supported as a separate SDK path. Successful initial HTTP player-stats completion is required between GPCM and PeerChat. Local implementations now include channel CRUD/relay, GPSP `searchunique` profile lookup, LAN NATNEG v3 rendezvous and authenticated GStats snapshot ingestion. See CURRENT.md for tested behavior and unresolved gameplay/statistics contracts.


## Room metadata and management

The game uses GameSpy channel metadata in addition to IRC membership. GETCKEY /
SETCKEY address per-player keys inside a room; GETCHANKEY / SETCHANKEY address
room keys; GETKEY / SETKEY address global player keys. Getters preserve the
request cookie and requested value order. Numeric replies 700¨C704 have the SDK
parameter counts, and wildcard member enumeration includes its completion reply.
Keys prefixed b_ broadcast changes using the BCAST cookie. An empty value removes
a key; part, kick, disconnect and channel deletion remove the corresponding
membership metadata.

For LIST with the k option, numeric 322 still has four parameters, but its final
field contains backslash-separated topic and limit key/value pairs. The game's
room-list callback skips entries without the topic key. Plain LIST retains the
ordinary topic field. TOPIC, MODE and SETGROUP updates feed subsequent listings.

Management includes invitations, password/limit/invite-only checks, kicks,
operator/voice modes, ban addition/removal/listing, WHO/WHOIS, nickname changes,
owner succession and deletion when the last member leaves. Nickname changes
update live routing and metadata without changing the persistent account identity.
UTM/ATM bodies remain opaque; message ACTION envelopes retain their SOH bytes.

Encrypted two-client tests exercise the lifecycle and SDK response shapes.
These tests do not establish real-console gameplay or automatic stats updates.
